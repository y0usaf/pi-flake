# Research: cmux AI-agent notifications

## Summary

At repository `main` commit [`f7a6f559a4a4a1de725a57c43df255949af48431`](https://github.com/manaflow-ai/cmux/commit/f7a6f559a4a4a1de725a57c43df255949af48431), cmux does **not** infer “the user’s overall task is complete.” Agent integrations translate agent lifecycle hooks into notifications, normally at a **turn boundary**; explicit permission/wait/error payloads are classified separately when an agent supplies them. For Pi specifically, cmux emits a completion notification only after Pi reports `agent_settled` and `ctx.isIdle()` (or immediately at `agent_end` on Pi versions before 0.80.5), and the Pi bridge has no separate “waiting for user input” notification event.

This is directly relevant to Pi Atelier: treat cmux’s Pi alert as **“the current agent turn settled and Pi is idle”**, not proof that a multi-turn task/plan is finished and not a reliable semantic signal that a question is awaiting an answer.

## Findings

1. **[High] Pi completion means settled turn, not completed task.** The installed Pi extension (`CLI/CMUXCLI+PiExtensionSourcePart2.swift`, `cmuxPiSessionExtension`, `publishPendingCompletion`) records the last result on `agent_end`. On Pi ≥0.80.5 it waits for `agent_settled`, checks `ctx.isIdle()`, then sends a `notification` with the last assistant text (fallback `"Task completed"`) followed by `stop`. `supportsAgentSettled()` in `CLI/CMUXCLI+PiExtensionSourcePart1.swift` enables that path at version 0.80.5; older Pi versions publish at `agent_end` because they lack `agent_settled`. There is no elapsed-runtime/minimum-duration gate. [Part 1](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/CMUXCLI%2BPiExtensionSourcePart1.swift) · [Part 2](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/CMUXCLI%2BPiExtensionSourcePart2.swift)

2. **[High] Pi does not distinguish task completion from waiting for user input.** The Pi extension subscribes to `session_start`, `before_agent_start`, `tool_execution_start`, `tool_execution_end`, `agent_end`, `agent_settled`, and `session_shutdown`. It emits one completion-shaped `notification` at settlement; it does not subscribe to a question, permission, or input-request event. Tool events go to Feed telemetry rather than this notification path. Therefore a Pi response ending in a question can still arrive as category/completion text determined from the payload, but the bridge itself supplies `notification.type` from `stopReason` or fallback `completed` and does not mark it as a blocking input request. [Source: `cmuxPiSessionExtension`](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/CMUXCLI%2BPiExtensionSourcePart2.swift)

3. **[High] Generic classification is payload-text/type based, not terminal-output or model-state inference.** `CLI/AgentHookNotificationPolicy.swift`, `AgentHookNotificationClassifier.classify`, combines the hook `signal` and `message`, lowercases them, and checks in this order: permission/approval → `.needsInput`/`needs-permission`; error/failure → `.error`/ungated `other`; completion tokens (`done`, `succeed*`, `complet*`, `finish*`, `success*`) → `.idle`/`turn-complete`; waiting tokens (`idle`, `wait*`, contextual `input`, or question/response cues) → `.needsInput`/`idle-reminder`; arbitrary nonempty text → `Attention` with no status; empty fallback → `.needsInput`. Because completion is tested before waiting, a message containing both classes is classified as completion. [Source](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/AgentHookNotificationPolicy.swift)

4. **[High] Claude has stronger—but still lifecycle-based—blocking-state logic.** Current code stores runtime lifecycle (`running`, `idle`, `needsInput`, `error`) in `CLI/cmux.swift` (`ClaudeHookSessionRecord`). A genuine permission/error or question path can remain `needsInput`; turn-end completion is idle. Claude Stop payloads additionally inspect unfinished `background_tasks`/`session_crons`; a pending flag is attached to notification metadata. `Sources/AgentNotificationGate.swift`, `agentNotificationShouldDeliver`, defaults turn-complete notifications to `whenIdle` (deliver only when `pending == false`), always lets the user choose `always`/`never`, and suppresses idle reminders while work remains. An upstream Claude `idle_prompt` is documented in the source as arriving about 60 seconds later; that delay is generated by Claude, not a cmux task-duration timer. [Session record/source](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/cmux.swift) · [Gate](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/AgentNotificationGate.swift) · [Merged implementation discussion](https://github.com/manaflow-ai/cmux/pull/7129)

5. **[Medium] No general “long task” threshold exists.** Normal CLI, OSC, and agent-hook notifications are event-driven and immediate after their source event/policy processing. The Pi extension’s `spawnSync` timeout is 5 seconds, but that is a hook-command failure bound, not a notification eligibility threshold. Separate notification policy hooks may be configured with their own timeout (example: 20 seconds), and hook failure falls back to default behavior. The documented “notify after long command” helper does not measure duration—it always notifies after the wrapped command. [Notifications docs](https://cmux.com/docs/notifications) · [Pi `runCmux`](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/CMUXCLI%2BPiExtensionSourcePart1.swift)

6. **[Medium] Deduplication has two distinct layers.**
   - **Agent-hook emission dedupe:** `AgentHookNotificationPolicy.dedupeFingerprint` applies only to `grok` and `antigravity`, not Pi or Claude generally. Idle uses one `idle-turn` fingerprint; other statuses use status plus stable FNV-1a body hash. `ClaudeHookSessionStore.recentlyEmittedNotification` retains fingerprints for 60 minutes, with `markNotificationEmitted` keeping at most 16 entries. Prompt submission clears/re-arms where the handler invokes `clearNotificationEmission`. Thus Pi completion events are not protected by this agent allowlist; Pi instead consumes its in-memory `pendingCompletion` and marks the turn stopped to avoid duplicate settlement delivery during one process run.
   - **Displayed-notification coalescing:** `TerminalNotificationStore.recordNotification` removes any existing notification for the same workspace+surface before inserting the new one and removes its delivered/pending macOS banner. This is last-notification-per-pane replacement, not semantic equality dedupe. [Policy](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/AgentHookNotificationPolicy.swift) · [Session-store symbols](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/cmux.swift) · [Display store](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/TerminalNotificationStore.swift)

7. **[Medium] Focus suppresses the external banner, not notification recording.** `TerminalNotificationStore.shouldSuppressExternalDelivery` suppresses external delivery only when a main cmux terminal window is focused **and** the originating workspace is selected **and** its originating surface is focused (`surfaceId == nil` also counts as focused). Settings/About/debug windows do not count as app focus (`AppFocusState.isAppFocused`). The notification is still recorded; for an unread focused notification the store sets a focused-read pane indicator. Suppressed delivery runs local feedback, so configured sound/custom-command effects can still occur even when the macOS banner is withheld. [Source: `AppFocusState`, `shouldSuppressExternalDelivery`, `deliverNotificationSideEffects`](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/TerminalNotificationStore.swift)

8. **[Medium] Official documentation overstates/abstracts suppression compared with this source snapshot.** The docs say desktop alerts are suppressed when “the cmux window is focused,” “the specific workspace … is active,” or “the notification panel is open.” In the inspected source, focus and active origin are conjunctive and surface-specific. I did not locate a separate notification-panel-open test in the terminal store’s final delivery gate. For Pi Atelier, rely on the source behavior above; treat panel-open suppression as unverified/stale documentation at this commit. [Docs](https://cmux.com/docs/notifications) · [Store source](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/TerminalNotificationStore.swift)

9. **[Medium] Supported ingress/system paths are macOS-centric.** cmux is a native macOS terminal. Notification ingress is `cmux notify`, OSC 9, OSC 99 (Kitty rich notifications with IDs), and OSC 777 (RXVT title/body). Native desktop delivery uses `UNUserNotificationCenter`; in-app history, unread badges, pane rings/flashes, Dock badge, sound, and a custom `/bin/sh -c` command are separate effects. tmux requires `allow-passthrough on` and wrapped escape sequences. [README](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/README.md) · [Notification protocols/docs](https://cmux.com/docs/notifications) · [Native store](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/TerminalNotificationStore.swift)

10. **[Low] Optional iPhone forwarding mirrors only unsuppressed desktop notifications.** `TerminalNotificationStore.deliverNotificationSideEffects` calls `PhonePushClient.forward` only on the normal desktop-delivery lane and only when `effects.desktop` is enabled; the comment states forwarding is opt-in and off by default. Focus-suppressed notifications are not forwarded. This is a mirror, not an independent agent-event classifier. [Source](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/TerminalNotificationStore.swift)

11. **[Medium] Raw terminal notifications are deliberately suppressed for hook-integrated agents.** `Workspace.suppressesRawTerminalNotification(panelId:)` returns true when a panel has a structured agent-hook PID (and optionally for managed subagents). This prevents raw OSC and the richer hook bridge from double-notifying. Claude’s `PushNotification` tool is therefore explicitly bridged via `PostToolUse`; a push reported by Claude as skipped is not duplicated. [Workspace symbol](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/Workspace%2BPanelLifecycle.swift) · [Agent-hooks docs](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/docs/agent-hooks.md)

12. **[Medium] Fallback behavior is intentionally fail-open for presentation, but hooks can no-op when cmux context is missing.**
   - Notification policy hook failure/timeout/invalid JSON applies default notification effects and posts a throttled “Notification Hook Failed” alert (`TerminalNotificationStore.reportNotificationHookFailure`, 300-second per-hook throttle).
   - If macOS notification authorization is unavailable/denied or scheduling fails, the store invokes local fallback feedback rather than silently discarding every effect; the in-app record/unread state already exists.
   - Generated agent hook commands no-op if `CMUX_SURFACE_ID` is missing, the integration disable variable is `1`, or no cmux executable is found. The Pi extension likewise returns without routing outside a cmux surface and logs/warns when its cmux subprocess fails.
   - tmux/SSH transport must pass the OSC sequence through; otherwise cmux never receives it. [Store](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/Sources/TerminalNotificationStore.swift) · [Generic hook wrapper](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/CMUXCLI%2BAgentHookDefinitions.swift) · [Pi extension](https://github.com/manaflow-ai/cmux/blob/f7a6f559a4a4a1de725a57c43df255949af48431/CLI/CMUXCLI%2BPiExtensionSourcePart2.swift) · [tmux docs](https://cmux.com/docs/notifications)

## Pi Atelier implications

- Do not interpret a cmux Pi notification as an authoritative workflow/task-complete event. It is a settled/idle turn signal.
- Do not rely on cmux’s current Pi integration to distinguish “answer required” from ordinary idle completion. If Pi Atelier needs that distinction, emit explicit categorized notification metadata or add a dedicated Pi question/permission event bridge.
- Expect every Pi turn to be eligible regardless of how short it was. Apply any “notify only after N seconds” policy in Pi Atelier or a cmux notification policy hook.
- Expect replacement of the prior notification in the same pane and focus suppression of the external banner; use cmux’s in-app unread/history or an explicit hook/command if every event must be durably observed.

## Gaps and residual risks

- **Medium:** The Pi agent package event contract was not independently examined because the scope required cmux primary sources only. The cmux extension’s subscribed events establish cmux behavior, but whether a newer Pi exposes an unused dedicated question/permission event remains unknown.
- **Medium:** The official web docs’ “notification panel open” suppression statement was not found in the inspected final-delivery source and conflicts with the source’s conjunctive focused-origin rule. It may be implemented in another UI layer or the docs may be stale.
- **Low:** cmux `main` evolves rapidly. Findings are attested only to commit `f7a6f559a4a4a1de725a57c43df255949af48431`; release builds may lag or differ.
- **Low:** Authorization/scheduling fallback invokes local feedback according to effect flags and authorization state. The exact user-perceived result depends on sound/custom-command settings and macOS authorization.
