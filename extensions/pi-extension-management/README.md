# pi-extension-management

Pi extension that manages a disabled-extensions list from an `/extensions` menu, persists it in `~/.pi/agent/extension-settings.json`, and applies changes in-session through pi's `/reload` machinery.

## What it does

- discovers extensions from the same places pi does:
  - `PI_DEFAULT_PACKAGES` package roots (the Nix bundle) — `extensions/` subdirectories
  - `~/.pi/agent/extensions/` (global auto-load)
  - `<cwd>/.pi/extensions/` (project auto-load)
- persists disabled extensions globally in `~/.pi/agent/extension-settings.json`
- mirrors the disabled list into `process.env.PI_EXT_DISABLED` (comma-separated)
- toggles apply immediately: settings write + env update + `ctx.reload()`
- never lists itself (`extension-management`): disabling the manager would lock you out

## How a disabled extension is actually stopped

Two levers, one per source:

| Source | Lever |
|---|---|
| bundle (`PI_DEFAULT_PACKAGES`) | a Nix-generated `.pi-gate.ts` shim prepended to each bundled extension's `pi.extensions`; the gate returns early when its name is in `PI_EXT_DISABLED` |
| global/project dirs | a `-pattern` entry in pi's own `settings.json` `extensions` array — the same mechanism `pi config` writes |

The gate shim is generated by `lib.piWithExtensions` in the pi-flake root `flake.nix`. On `/reload`, pi clears its extension module cache and re-evaluates every extension file, so the gate re-reads `PI_EXT_DISABLED` each time. The env var is inherited by child pi processes, so spawned sub-agents keep the same disables.

A disabled bundle extension's module still evaluates (top-level imports run); only its factory call is skipped, so it registers no tools, commands, or hooks.

## Requirements

- Pi / `@earendil-works/pi-coding-agent` `^0.74.0`
- `@earendil-works/pi-tui` `^0.74.0` (provided by compatible Pi extension environments)

## Usage

```bash
# Install as a pi package
pi install ./extensions/pi-extension-management

# Or load directly for one session
pi -e ./extensions/pi-extension-management/src/index.ts
```

Commands:
- `/extensions` — open the disabled-extensions menu (toggling reloads pi)
- `/extensions-status` — show settings path, env projection, discovered sources, disabled list

## Settings file

`~/.pi/agent/extension-settings.json`

```json
{
  "version": 1,
  "disabledExtensions": ["caveman", "extensions/foo.ts"]
}
```

Identities:

- bundle extensions use their directory name under the bundle's `share/pi/extensions/` (e.g. `caveman`)
- global/project dir extensions use the settings pattern pi matches: path relative to the base dir (e.g. `extensions/foo.ts`)

Notes:

- settings are global to the current Pi agent home (`~/.pi/agent`) and shared across projects unless you change that home
- toggling a global/project dir extension writes into pi's own `settings.json`; that file is normally user-writable — if your setup symlinks it from the Nix store, those writes fail and only bundle toggles work
- disabling an extension does not remove skills, prompts, or themes a package may also ship; those are resolved by pi's resource loader independently of the extension factory
- after `ctx.reload()`, this extension's own command context is replaced; the toggle is always the handler's last action
